Plantilla de Autenticación — Puesta en marcha

Pasos para clonar, vincular, configurar y levantar la plantilla reutilizable de autenticación (Clean Architecture / SOLID) en un proyecto nuevo. Pensada para seguirse de punta a punta, sin conocimiento previo del repositorio.

flowchart TD
    A["Paso 1
Clonar el repositorio"] --> B["Paso 2
Vincular repo remoto nuevo"]
    B --> C["Paso 3
Entorno virtual + dependencias + .env"]
    C --> D["Paso 4
Tests + migraciones + servidor local"]
    D --> E["Paso 5
Extender tablas / actualizaciones"]
1

Clonar el repositorio

Opción A — Sin historial de commits anterior

Usá esta opción si querés que el nuevo proyecto arranque con un historial de git propio, sin los commits de la plantilla.

PS C:\Projects> git clone https://github.com/tu-usuario/Plantilla-Autentificacion-POO.git MiNuevoProyecto
PS C:\Projects> cd MiNuevoProyecto
PS C:\Projects\MiNuevoProyecto> Remove-Item -Recurse -Force .git
PS C:\Projects\MiNuevoProyecto> git init
PS C:\Projects\MiNuevoProyecto> git add .
PS C:\Projects\MiNuevoProyecto> git commit -m "feat: initial commit from authentication boilerplate"

Opción B — Conservando el historial anterior

Si te sirve mantener el historial de commits de la plantilla como referencia:

PS C:\Projects> git clone https://github.com/tu-usuario/Plantilla-Autentificacion-POO.git MiNuevoProyecto
PS C:\Projects> cd MiNuevoProyecto

No se necesitan más pasos de este punto para este caso.

2

Vinculación con el nuevo repositorio remoto (GitHub)

2.1 — Diagnóstico inicial de remotes

PS C:\Projects\MiNuevoProyecto> git remote -v

Permite ver a qué repositorio está vinculado el proyecto actualmente.

2.2 y 2.3 — El error "remote origin already exists" y su solución

Cuando cloná el repo, el alias origin ya apunta a la plantilla original. Según el caso, usá:

  • git remote add — cuando el alias NO existe (por ejemplo, tras un git init desde cero).
    git remote add origin <URL-NUEVO-REPO>
  • git remote set-url — cuando origin ya existe y querés reapuntarlo.
    git remote set-url origin <URL-NUEVO-REPO>

Comando de re-vinculación directa (caso más común, cuando origin ya existe):

PS C:\Projects\MiNuevoProyecto> git remote set-url origin https://github.com/tu-usuario/MiNuevoProyecto.git

2.4 — Publicación en el repositorio remoto

# 1. Renombrar la rama local a main
PS C:\Projects\MiNuevoProyecto> git branch -M main

# 2. Publicar el código y fijar upstream
PS C:\Projects\MiNuevoProyecto> git push -u origin main

# 3. Verificación final
PS C:\Projects\MiNuevoProyecto> git remote -v
# Debe confirmar:
# origin  https://github.com/tu-usuario/MiNuevoProyecto.git (fetch)
# origin  https://github.com/tu-usuario/MiNuevoProyecto.git (push)
3

Configuración del entorno virtual Python

3.1 — Crear y activar el entorno virtual

PS C:\Projects\MiNuevoProyecto> python -m venv venv

# Si al activar da error "running scripts is disabled":
PS C:\Projects\MiNuevoProyecto> Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

PS C:\Projects\MiNuevoProyecto> .\venv\Scripts\Activate.ps1
(venv) PS C:\Projects\MiNuevoProyecto>

3.2 — Instalar dependencias

(venv) PS C:\Projects\MiNuevoProyecto> python -m pip install --upgrade pip
(venv) PS C:\Projects\MiNuevoProyecto> pip install -r requirements.txt

3.3 — Variables de entorno (.env)

Copiá el archivo de ejemplo (ubicado en la carpeta de guía de uso):

(venv) PS C:\Projects\MiNuevoProyecto> Copy-Item .env.example .env

3.3.A — Generar una nueva clave secreta para JWT:

(venv) PS C:\Projects\MiNuevoProyecto> python -c "import secrets; print(secrets.token_hex(32))"
# Copiá la salida y pegala en SECRET_KEY dentro de .env

3.3.B — Base de datos PostgreSQL dedicada:

(venv) PS C:\Projects\MiNuevoProyecto> psql -U postgres -c "CREATE DATABASE mi_nuevo_proyecto_db;"

Cargá esa URL de conexión en el campo DATABASE_URL de tu .env.

4

Verificación operativa final (pre-flight checks)

4.1 — Ejecutar la suite de tests (opcional)

(venv) PS C:\Projects\MiNuevoProyecto> pytest
# Confirmar salida verde, ej: "130 passed in 1.45s"

4.2 — Ejecutar migraciones de Alembic

Requiere la base de datos ya creada (vacía) y su URL guardada en DATABASE_URL dentro de .env.

(venv) PS C:\Projects\MiNuevoProyecto> alembic upgrade head
# Verificar la creación correcta de las tablas de auth

4.3 — Levantar el servidor de desarrollo

(venv) PS C:\Projects\MiNuevoProyecto> uvicorn app.main:app --reload
Verificar antes de correrlo: Este comando asume que el punto de entrada vive en app/main.py. Si tu estructura real usa otro path (por ejemplo src.main:app), ajustá el comando acorde a como esté organizado tu proyecto antes de ejecutarlo.
5

Actualizaciones futuras

Una vez que la plantilla está funcional, podés extenderla según las reglas de negocio del proyecto. Tené en cuenta:

  • La tabla principal es auth_user. No debería modificarse en profundidad salvo necesidad real.
  • La tabla usuario existe vacía, relacionada 1 a 1 con auth_user por su mismo id. Está pensada para ampliar el catálogo de datos del usuario sin tocar la tabla de autenticación — se puede extender tanto como lo requieran las reglas de negocio.
  • Modificar una tabla existente probablemente implique actualizar también los DTOs y modelos de recepción (no de tabla) asociados, además de las verificaciones correspondientes.
