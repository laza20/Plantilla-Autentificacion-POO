Guía de uso

Plantilla de Autenticación — Puesta en marcha

Pasos para clonar, vincular, configurar y levantar la plantilla reutilizable de autenticación (Clean Architecture / SOLID) en un proyecto nuevo. Pensada para seguirse de punta a punta, sin conocimiento previo del repositorio.

flowchart TD
    A["Paso 1
Clonar el repositorio"] --> B["Paso 2
Vincular repo remoto nuevo"]
    B --> C["Paso 3
Entorno virtual + dependencias + .env"]
    C --> D["Paso 4
Tests + migraciones + servidor local"]
    D --> E["Paso 5
Extender tablas / actualizaciones"]
1

Clonar el repositorio

Opción A — Sin historial de commits anterior

Usá esta opción si querés que el nuevo proyecto arranque con un historial de git propio, sin los commits de la plantilla.

PS C:\Projects> git clone https://github.com/tu-usuario/Plantilla-Autentificacion-POO.git MiNuevoProyecto
PS C:\Projects> cd MiNuevoProyecto
PS C:\Projects\MiNuevoProyecto> Remove-Item -Recurse -Force .git
PS C:\Projects\MiNuevoProyecto> git init
PS C:\Projects\MiNuevoProyecto> git add .
PS C:\Projects\MiNuevoProyecto> git commit -m "feat: initial commit from authentication boilerplate"

Opción B — Conservando el historial anterior

Si te sirve mantener el historial de commits de la plantilla como referencia:

PS C:\Projects> git clone https://github.com/tu-usuario/Plantilla-Autentificacion-POO.git MiNuevoProyecto
PS C:\Projects> cd MiNuevoProyecto

No se necesitan más pasos de este punto para este caso.

2

Vinculación con el nuevo repositorio remoto (GitHub)

2.1 — Diagnóstico inicial de remotes

PS C:\Projects\MiNuevoProyecto> git remote -v

Permite ver a qué repositorio está vinculado el proyecto actualmente.

2.2 y 2.3 — El error "remote origin already exists" y su solución

Cuando cloná el repo, el alias origin ya apunta a la plantilla original. Según el caso, usá:

  • git remote add — cuando el alias NO existe (por ejemplo, tras un git init desde cero).
    git remote add origin <URL-NUEVO-REPO>
  • git remote set-url — cuando origin ya existe y querés reapuntarlo.
    git remote set-url origin <URL-NUEVO-REPO>

Comando de re-vinculación directa (caso más común, cuando origin ya existe):

PS C:\Projects\MiNuevoProyecto> git remote set-url origin https://github.com/tu-usuario/MiNuevoProyecto.git

2.4 — Publicación en el repositorio remoto

# 1. Renombrar la rama local a main
PS C:\Projects\MiNuevoProyecto> git branch -M main

# 2. Publicar el código y fijar upstream
PS C:\Projects\MiNuevoProyecto> git push -u origin main

# 3. Verificación final
PS C:\Projects\MiNuevoProyecto> git remote -v
# Debe confirmar:
# origin  https://github.com/tu-usuario/MiNuevoProyecto.git (fetch)
# origin  https://github.com/tu-usuario/MiNuevoProyecto.git (push)
3

Configuración del entorno virtual Python

3.1 — Crear y activar el entorno virtual

PS C:\Projects\MiNuevoProyecto> python -m venv venv

# Si al activar da error "running scripts is disabled":
PS C:\Projects\MiNuevoProyecto> Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

PS C:\Projects\MiNuevoProyecto> .\venv\Scripts\Activate.ps1
(venv) PS C:\Projects\MiNuevoProyecto>

3.2 — Instalar dependencias

(venv) PS C:\Projects\MiNuevoProyecto> python -m pip install --upgrade pip
(venv) PS C:\Projects\MiNuevoProyecto> pip install -r requirements.txt

3.3 — Variables de entorno (.env)

El archivo de ejemplo se llama env_example.txt y está en la carpeta guia de uso. Copialo a la raíz del proyecto con el nombre .env. Como la carpeta tiene espacios, la ruta va entre comillas:

(venv) PS C:\Projects\MiNuevoProyecto> Copy-Item ".\guia de uso\env_example.txt" ".env"
Si el comando falla: Verificá el nombre exacto de la carpeta con Get-ChildItem (puede llevar tilde: guía de uso) o autocompletá la ruta con la tecla Tab.

3.3.A — Generar una nueva clave secreta para JWT:

(venv) PS C:\Projects\MiNuevoProyecto> python -c "import secrets; print(secrets.token_hex(32))"
# Copiá la salida y pegala en SECRET_KEY dentro de .env

3.3.B — Base de datos PostgreSQL dedicada:

Requiere PostgreSQL instalado y con el servicio corriendo. Podés comprobarlo así:

(venv) PS C:\Projects\MiNuevoProyecto> Get-Service *postgres*
# Debe mostrar Status: Running

Luego creá la base (te pide la contraseña del usuario postgres, la que definiste al instalar):

(venv) PS C:\Projects\MiNuevoProyecto> psql -U postgres -c "CREATE DATABASE mi_nuevo_proyecto_db;"
# Salida esperada: CREATE DATABASE
¿Apareció "psql : El término 'psql' no se reconoce como nombre de un cmdlet…"? PostgreSQL está instalado, pero su carpeta bin no está en el PATH (el instalador de Windows no siempre lo agrega). Seguí la sección 3.3.B.1.

3.3.B.1 — Solución si "psql" no se reconoce

1. Detectar la versión instalada (el nombre de la carpeta es el número de versión):

(venv) PS C:\Projects\MiNuevoProyecto> Get-ChildItem "C:\Program Files\PostgreSQL"
# Ejemplo de salida: una carpeta llamada 18

2. Opción rápida — solo para esta terminal. Reemplazá 18 por tu versión:

(venv) PS C:\Projects\MiNuevoProyecto> $env:Path += ";C:\Program Files\PostgreSQL\18\bin"
(venv) PS C:\Projects\MiNuevoProyecto> psql -U postgres -c "CREATE DATABASE mi_nuevo_proyecto_db;"

3. Alternativa — llamar a psql con la ruta completa, sin tocar el PATH:

(venv) PS C:\Projects\MiNuevoProyecto> & "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres -c "CREATE DATABASE mi_nuevo_proyecto_db;"

4. Opción permanente — se hace una sola vez por equipo:

(venv) PS C:\Projects\MiNuevoProyecto> [Environment]::SetEnvironmentVariable("Path", $env:Path + ";C:\Program Files\PostgreSQL\18\bin", "User")

Cerrá y volvé a abrir la terminal para que el cambio tenga efecto.

Si Get-Service *postgres* no devuelve nada: PostgreSQL no está instalado. Instalalo antes de continuar; esta guía asume un servidor PostgreSQL local ya disponible.

3.3.C — Armar la DATABASE_URL en el .env

Una vez creada la base, cargá la URL de conexión en el campo DATABASE_URL del .env. Formato general:

DATABASE_URL=postgresql+DRIVER://USUARIO:CONTRASEÑA@HOST:PUERTO/NOMBRE_BD

Ejemplo listo para pegar y modificar (usa la base creada en 3.3.B):

DATABASE_URL=postgresql+psycopg2://postgres:TU_PASSWORD@localhost:5432/mi_nuevo_proyecto_db

Qué reemplazar en cada parte:

  • DRIVER — el que use la plantilla (ver abajo).
  • USUARIO — postgres por defecto.
  • TU_PASSWORD — la contraseña del usuario postgres definida al instalar PostgreSQL.
  • localhost — el host; queda así si PostgreSQL corre en tu máquina.
  • 5432 — el puerto por defecto de PostgreSQL.
  • mi_nuevo_proyecto_db — el nombre exacto usado en el CREATE DATABASE.

Prefijos según el driver:

  • postgresql+psycopg2:// — SQLAlchemy síncrono con psycopg2.
  • postgresql+psycopg:// — SQLAlchemy con psycopg 3.
  • postgresql+asyncpg:// — SQLAlchemy asíncrono con asyncpg.

Si el .env de ejemplo ya trae una URL, conservá su prefijo y cambiá solo el resto.

Contraseña con caracteres especiales: Si contiene @, :, /, # o %, hay que codificarla para que la URL no se rompa. Generá la versión codificada así y pegala en la URL: 
(venv) PS C:\Projects\MiNuevoProyecto> python -c "import urllib.parse; print(urllib.parse.quote_plus('mi@pass:word'))"
# Salida: mi%40pass%3Aword
Seguridad: El .env contiene la contraseña y la SECRET_KEY. Confirmá que .env figura en .gitignore antes de hacer commit.
¿Aparece "python-dotenv could not parse statement starting at line N"? Esa línea del .env tiene un formato inválido y no se está leyendo. Mirala con (el índice arranca en 0, por eso se resta 1 al número de línea): 
(venv) PS C:\Projects\MiNuevoProyecto> (Get-Content .env)[N-1]
Las causas habituales son un valor con espacios o # sin comillas, un comentario sin # al inicio, o una línea sin =. Si el valor tiene espacios, va entre comillas: CLAVE="valor con espacios".
4

Verificación operativa final (pre-flight checks)

4.1 — Ejecutar la suite de tests (opcional)

(venv) PS C:\Projects\MiNuevoProyecto> pytest
# Confirmar salida verde, ej: "130 passed in 1.45s"

Los tests usan stubs y no necesitan tablas: ejecutarlos no debe crear ni modificar el esquema de la base. El esquema lo crea únicamente Alembic (paso 4.2).

Verificación opcional: Con la base recién creada y vacía, después de correr pytest el comando psql -U postgres -d mi_nuevo_proyecto_db -c "\dt" debe devolver que no hay relaciones. Si aparecen tablas, algo del proyecto (por ejemplo un SQLModel.metadata.create_all(engine) a nivel de módulo en main.py) está creando el esquema por fuera de Alembic y va a provocar el error de la sección 4.2.

4.2 — Ejecutar migraciones de Alembic

Requiere la base de datos ya creada (vacía) y su URL guardada en DATABASE_URL dentro de .env.

Alembic es el único que crea el esquema: la aplicación no crea tablas al arrancar. Por eso este paso es obligatorio antes de levantar el servidor (4.3).

(venv) PS C:\Projects\MiNuevoProyecto> alembic upgrade head
# Verificar la creación correcta de las tablas de auth

(venv) PS C:\Projects\MiNuevoProyecto> alembic current
# Debe mostrar la revisión aplicada, ej: 0767bfec6564 (head)
¿Apareció "DuplicateObject: ya existe un tipo «estado_entidad»"? La base no estaba vacía: ya tenía el tipo o las tablas, creados por algo distinto a Alembic (por ejemplo, una base usada antes en otro intento). Comprobalo: 
(venv) PS C:\Projects\MiNuevoProyecto> psql -U postgres -d mi_nuevo_proyecto_db -c "\dT"
(venv) PS C:\Projects\MiNuevoProyecto> psql -U postgres -d mi_nuevo_proyecto_db -c "\dt"
Si aparecen estado_entidad o tablas y la base es descartable, recreala y volvé a migrar: 
(venv) PS C:\Projects\MiNuevoProyecto> psql -U postgres -c "DROP DATABASE mi_nuevo_proyecto_db;"
(venv) PS C:\Projects\MiNuevoProyecto> psql -U postgres -c "CREATE DATABASE mi_nuevo_proyecto_db;"
(venv) PS C:\Projects\MiNuevoProyecto> alembic upgrade head
Antes del DROP, confirmá que la base no tenga datos que necesites y cerrá las conexiones abiertas (servidor, pgAdmin); si no, PostgreSQL rechaza el borrado. Si la lista sale vacía, Alembic está conectando a otra base: revisá el nombre al final de DATABASE_URL en el .env.

4.3 — Levantar el servidor de desarrollo

(venv) PS C:\Projects\MiNuevoProyecto> uvicorn app.main:app --reload
Verificar antes de correrlo: Este comando asume que el punto de entrada vive en app/main.py. Si tu estructura real usa otro path (por ejemplo src.main:app), ajustá el comando acorde a como esté organizado tu proyecto antes de ejecutarlo.
Si aparece un error del tipo "la relación … no existe": Faltó aplicar las migraciones. Volvé al paso 4.2 y ejecutá alembic upgrade head.
5

Actualizaciones futuras

Una vez que la plantilla está funcional, podés extenderla según las reglas de negocio del proyecto. Tené en cuenta:

  • La tabla principal es auth_user. No debería modificarse en profundidad salvo necesidad real.
  • La tabla usuario existe vacía, relacionada 1 a 1 con auth_user por su mismo id. Está pensada para ampliar el catálogo de datos del usuario sin tocar la tabla de autenticación — se puede extender tanto como lo requieran las reglas de negocio.
  • Modificar una tabla existente probablemente implique actualizar también los DTOs y modelos de recepción (no de tabla) asociados, además de las verificaciones correspondientes.
  • Como la aplicación no crea tablas al arrancar, todo cambio de esquema requiere una migración de Alembic: un modelo nuevo o modificado no se refleja en la base hasta que se genera y aplica la migración.
(venv) PS C:\Projects\MiNuevoProyecto> alembic revision --autogenerate -m "descripcion del cambio"
# Revisar el archivo generado en alembic/versions/ antes de aplicarlo

(venv) PS C:\Projects\MiNuevoProyecto> alembic upgrade head
Requisito para el autogenerate: alembic/env.py debe importar los modelos de tabla y definir target_metadata = SQLModel.metadata. Si falta alguno de los dos, Alembic no detecta los cambios y genera migraciones vacías.
